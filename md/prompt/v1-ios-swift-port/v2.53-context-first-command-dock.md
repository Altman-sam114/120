## 目标

把横屏 iOS RTS command dock 从“完整但需要滚动的工具列表”收敛为 Rusted Warfare 风格的上下文优先战术栏：

1. **Production fixture**：固定横屏云端 production screenshot 选中完成状态 `Land Factory` 后，dock 首屏无需滚动即可看到至少第一行生产单位入口；第一行按钮必须完整显示图标、可辨识名称或短名和必要的成本/人口/时间摘要，不得被 dock 边界、队列、底部裁切或 Tactical Map 遮挡。
2. **Combat fixture**：固定横屏云端 combat screenshot 中，`Move`、`Attack Move`、`Attack`、`Stop` 四个核心命令在首屏可见，无需滚动；命令顺序和视觉优先级应明显高于 Patrol、Guard、Repair、Reclaim、姿态和批量选择辅助操作。
3. **Target pending**：等待目标时的提示必须紧凑、可扫读、位于 dock 自身布局流中，不覆盖战场或 Tactical Map，不把首屏核心命令推到屏幕外；仍要明确当前命令和“点击可见目标/地点”的下一步。
4. **Pinch continuity**：`BattlefieldView.swift` 中 pinch 正常结束、第三指介入、触点 replacement、gesture cancel、地图 reset 及其他 teardown 路径，在释放 pinch lease 时统一写回 `lastMagnification = 1.0`；下一次 pinch 首帧不得沿用旧累计 magnification 而跳缩。
5. 保留所有现有 44pt 最小触控目标、Dynamic Type、VoiceOver、Reduce Motion、controller action、键盘快捷键、disabled 条件、selection Replace/Add、生产/升级上下文和辅助功能语义。

## Context-first 设计契约

### Dock composition

- 保持 `RootGameView` 的 status bar、battlefield、trailing/bottom dock 分区和 `.clipped()` 边界；不让任何 HUD view 使用 `overlay`/`zIndex` 覆盖战场来“显示首屏内容”。
- `TacticalCommandDockView` 的 header 必须是 compact context header，而不是重复展示完整 production queue/upgrade 详情；详细 queue 和 management 仍在 Production section 中。
- 选中完成状态 Land Factory 时，Production section 紧跟 header；在 compact trailing 的固定 dock 宽度下，第一行 production entry 的整块按钮必须首屏可见，不能依赖用户先滚动。
- 选中 combat unit 或 combat 多选时，Commands section 紧跟 header；primary command group 必须在首屏，secondary section 可以继续位于其后并滚动。
- 没有生产或 combat context 时，保留现有通用 section 条件和顺序，不能为了两个 fixture 删除玩家可用功能。
- `onChange(of: controller.dockSelectionIdentity)` 的回顶行为保留；不能因重新组合 section 造成选择刷新时自动滚到旧的 production queue 或 secondary group。

### Primary command group

- 首组只提升 presentation priority，不创建新 action。具体映射必须保持：
  - `Move` -> 现有 `toggleMoveCommand`
  - `Attack Move` -> 现有 `toggleAttackMoveCommand`
  - `Attack` -> 现有 `toggleAttackCommand`
  - `Stop` -> 现有 `issueStopCommand`
- 以上按钮仍分别服从 `canIssue...` / `isAwaiting...` 与 `showsStop`；不可通过无条件显示改变玩法。
- Awaiting target 时对应按钮继续显示取消图标/既有 title，target status 必须同时存在；不要用重排让用户误以为 command 已经提交。
- `Stop` 即使视觉上进入 primary，也不能清除不属于它的 pending state；沿用 controller 既有处理。
- 保留现有快捷键：Move、Attack Move、Patrol、Guard、Reclaim、Stop、Selection、Production、Build 等 shortcut 不得重绑或冲突。

### Compact target status

- 普通字号的 target pending 采用紧凑的 inline/card strip：图标 + `TARGET MODE` 或既有 command title + 一到两行可读状态；不显示大段重复说明。
- 不能用 `lineLimit(1)` 或极端缩放截断关键目标语义；较窄宽度应自然换行，accessibility size 可增加高度并允许 dock 滚动。
- status strip 必须使用既有 yellow/attention 边框或等价的非颜色差异；`accessibilityDifferentiateWithoutColor` 时保留更粗边框/图标。
- status 只能在 dock 的 VStack/ScrollView layout 中占位，不能 `position` 到战场上，也不能挡住 Tactical Map、selection box、command confirmation 或 target marker。
- 无 pending command 时的 `TacticalBattlefieldHintView` 可压缩为一行标题 + 短 detail，但必须保留对玩家操作有价值的提示和 VoiceOver 内容。

### Production first row

- 保留 production options 的数据顺序、`ForEach` identity 和 Shift+1-9 索引；不得重排单位造成快捷键与视觉入口不一致。
- compact trailing 仍应使用能容纳第一行的固定列数和稳定高度；不得让动态文本测量改变相邻 tile 的触控区域大小。
- 每个 production entry 最少保持：unit icon、短名/名称、metal、supply、build time；使用 `minimumScaleFactor` 时必须有合理下限且不可破坏 Dynamic Type 可读性。
- 队列当前项的 progress/当前单位和后续队列必须仍可访问；可把详细队列压到第一行之后，但不能删除、伪造或改动取消/退款/Repeat/Rally。
- Factory Tech 的 upgrade ready/upgrading/max tech 状态、按钮 action、benefit、取消入口和 VoiceOver 保持；只压缩 padding/层级，不改变 upgrade 条件。

## 保留契约清单

- 44pt：所有 Button、Picker、Segmented control、icon-only control 和 production entry 的有效 hit frame 至少 44pt；视觉 tile 可更紧凑，但 hit target 不得缩小。
- Dynamic Type：普通字号优先 compact layout；`dynamicTypeSize.isAccessibilitySize` 必须切换到可读的一列/自然换行布局，不能为了首屏硬塞或裁切文字。
- VoiceOver：保留每个 controller action 的 accessibility label/value/hint；若视觉上使用短名（如 `Arty`），accessibility 必须仍读完整 unit 名、成本、人口和时间。
- Reduce Motion：不得新增依赖动画的状态或任务；现有 transaction/sensory feedback/command confirmation 的 Reduce Motion 行为不变。
- Controller action/shortcut：不改任何 closure、键盘 shortcut、button title 的状态来源、disabled 条件、selection mode binding、production queue management 和 target cancellation。
- Core/JSON/save：不得修改 `swift/RustwarCore`、`GameState`、编码/解码、存档兼容或任何 gameplay state。
- 战场：不得改变 `BattlefieldView`、`BattlefieldScene`、Tactical Map 的输入、渲染、可见性、攻击范围、目标环、特效或相机行为。
- Pinch 例外：允许 `BattlefieldView` 仅为统一 teardown 复位 `lastMagnification`；除该复位外，战场输入、渲染、可见性、攻击范围、目标环、特效、相机行为和 zoom 数学必须不变。

## Pinch lease teardown 契约

- `lastMagnification` 是 `BattlefieldView` 的手势累计 presentation 状态，不是 Core、Controller、JSON 或存档状态。
- 正常 pinch end、第三指导致的序列取消、触点 replacement/未知 active 导致的拒绝、gesture cancel、地图 reset、sequence reset，以及任何释放 pinch owner/lease 的清理出口，都必须经过同一个 teardown helper 或等价的单一路径，并在释放 lease 时设置 `lastMagnification = 1.0`。
- 不得只在正常 `.onEnded` 复位；异常终止路径同样必须复位。不得在复位后继续使用旧 magnification 提交一次额外 zoom。
- 下一次 pinch 的首个 changed/value 必须以 `lastMagnification == 1.0` 为基线，再沿用现有增量/缩放算法；不得修改相机 zoom 算法、clamp、倍率、地图边界或 Controller API。
- teardown 必须保持 v2.52 的 owner/sequence quarantine：复位 magnification 不得重新取得 lease、解除 cancelled ID、恢复 `.possible`、提交 tap/area selection/command 或清除新序列状态。
- 该修复只处理 touch continuity 和 presentation cleanup；不新增 Core 单测依赖或任何新的测试框架。Agent B 只能做只读代码审查，云端 workflow 负责编译和固定截图。

## 已知验证缺口与风险

- 当前 CI 是静态源码/Core/build 加固定 iPhone 17 Pro production/combat 启动、横屏截图和像素探针；它没有 XCUITest、真实点击、滚动、Dynamic Type、VoiceOver、Reduce Motion、旋转、快捷键或真机性能自动化。

- 云端 iOS build、静态 production/combat PNG 和现有 Core/静态检查不能证明真实 pinch lease teardown；Agent C 必须把该项作为代码审查结论和明确 residual risk，不能宣称真实 pinch 已通过。
- 紧凑 target status 仍必须以可读性和 accessibility 为先；不能因为固定截图而隐藏完整提示、改变 pending 语义或让用户失去取消命令的路径。
