Agent A，2026-09-07。主任务顺序执行角色，不增开子智能体。前置：v2.87 最新 origin/main 的 C 结果包验收通过后才执行本轮 B。

## 实际问题

`BattlefieldView.updateMultitouchSelection` 在已有双指序列中要求 active IDs 等于原 pair。`TouchSequenceOwner.observe` 却允许正常 ended ID 进入 terminal 集合、保留另一只 active 手指。因此第一只手指先抬起时，view 会取消仍合法的序列。最终 finish 路径又没有明确等待两指结束，不能靠两个手指恰好同时抬起保证可靠性。

## 目标与实现边界

- 在 RustwarCore 增加独立、纯 Swift 的双指释放跟踪器（输入 active/ended/cancelled ID 集合），只服务触控生命周期，不进入 GameState/JSON。区分 tracking、releasing、complete、cancelled；正常 ended 累积，第三指/替换指/缺少 ended 的丢失/系统取消失败关闭。重复 terminal 不重复产生游戏命令。
- BattlefieldView 的 update/finish 共用该跟踪器。首指正常抬起时，用该帧最后位置分类并冻结 selection rectangle；剩余手指拖动不改变矩形，也不在等待期间把 undecided 升级成 selection。最后一指正常抬起后只提交一次。相机/input epoch 变化仍取消；pending command、pinch、长按、single tap/pan、Add/Replace、建筑 fallback 与现有 owner lease 保持。
- 不扩大到模型、战斗数值、UI 新页面、存档或 Web。后续仍需真实云端 UI 事件注入与更大范围触控重构，本轮纯状态测试不冒充真机手感证据。

### 接线细节

`synchronizeTouchOwner` 会把正常 ended IDs 放入其历史 terminal/quarantine 集合；因此 tracker 必须读取原始事件中属于 accepted pair 的 ended/cancelled，不能读取已经排除 terminal 的 active-only 数组。记录累计 ended，剩余指 active 与已结束指共同覆盖原 pair 才合法。首次 release 帧包含最后位置，之后的单指尾随移动不能扩大框选，也不能推迟到尾指结束才重新计算 dwell。

update 和 finish 都复用同一个 frame-update helper；当 onChanged 已收到完整 terminal 集合时可进入正式 finish，同一 owner lease 负责一次提交，随后迟到的 onEnded 不得重复提交。onEnded 若仍有合法 active finger，则只保留 releasing 状态。reset/cancel 必须清理 tracker。原 owner 的相机 lease、input epoch、第三指拒绝和 cancelled 路径先于 tracker 的完成判断，不能以 tracker 的 complete 绕过这些门控。

| 回归序列 | 预期 |
| --- | --- |
| 两指 active → 首指 ended/尾指 active → 尾指 ended | tracking → releasing → complete；只在 complete 提交 |
| 两指同时 ended | 直接 complete，保留最后有效框选几何 |
| 首指 ended 在后续 frame 重复出现 | 幂等累计，不取消、不重复提交 |
| 首指抬起后尾指移动或等待 | 范围与 intent 冻结，不把早抬的 undecided 变成 selection |
| 缺少 ended 的原指消失 | cancelled，不猜测正常抬起 |
| 第三指或替换 ID | cancelled |
| 任一原指 cancelled，含 releasing 阶段 | cancelled，无选择提交 |
| complete 后重复终止回调 | 旧 owner lease 无法再次 committed |
