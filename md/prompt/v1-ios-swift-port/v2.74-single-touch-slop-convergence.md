## 背景与问题

`BattlefieldView` 的单指 pan 在 12pt 激活，但 `commitSingleTouchTap` 仍允许手指从起点移动最多 18pt 后提交。12–18pt 之间因此存在语义冲突：drag owner 理应平移镜头，迟到或不同顺序的 context/tap callback 却仍可能提交选择、直接 Attack 或空地点 Attack-Move。v2.48 文档已经声明预览只在 12pt 以下存在，当前实现也应与这条合同收敛。

Rusted Warfare 移动端的核心手感是“点即选/下令，拖即移动视野”，边界必须互斥。v2.74 只统一 presentation 输入 slop，不改变直接点按命令或自动索敌规则。

## 目标

1. 用一个 `RustwarCore` 纯 policy 统一单指 pan activation、意图预览与 tap/command commit 的 12pt 边界。
2. travel `< 12pt` 时继续允许选择/Attack/Attack-Move 或 pending command 的预览与抬指提交。
3. travel `>= 12pt` 时立即清理预览，并在当前 touch sequence 内永久禁止 tap、context command 和 long press 提交；只允许既有 drag gesture 成为 pan/Select Area owner。
4. Core 边界测试覆盖 `<12`、`==12`、`>12`、负数和非有限输入；非法输入必须 fail closed。
5. 保持 44pt 实体命中、直接点敌 Attack、空地点 Attack-Move、Builder Move、双指框选、pinch、pending command、自动索敌和所有 Core 命令语义。

## 实现要求

### Core policy

- 新建无平台依赖的 `SingleTouchTravelPolicy`，唯一权威阈值为 `12.0`。
- 提供只接收 travel distance 的纯函数；仅有限、非负且严格小于 12 的输入允许 tap/preview，等于或超过阈值一律拒绝。
- 不把 SwiftUI、CGPoint、gesture owner 或命令逻辑引入 Core，不修改 `TouchSequenceOwner`。

### `BattlefieldView`

- `DragGesture.minimumDistance` 从 Core policy 派生，不保留第二个独立数值。
- context location 每次变化都更新当前触点；达到阈值时清理当前 sequence 的 preview，并 latch “已跨 pan 边界”。即使手指随后回到 12pt 内，同一 sequence 也不得恢复 preview 或提交命令。
- `commitSingleTouchTap` 必须要求有效起点，且同时满足未 latch 与 Core policy；删除旧 18pt commit 判断。
- long press 保留 `minimumDuration=0.45` / `maximumDistance=18` 的 SwiftUI 识别配置，但跨过统一 12pt 后不得提交；pan 仍由现有 shared owner 独占 claim。
- 每次 context lifecycle 收尾、新 sequence、cancel/reset、pan/multitouch/pinch 结束后正确清理 latch，不让旧触摸污染下一枚 fresh touch。
