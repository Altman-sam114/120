# v1.13 / iOS native patrol command foundation

## Agent A brief

Version: `v1.13`

Goal: add a native iOS single-unit patrol command so the SwiftUI/SpriteKit app can issue a patrol endpoint to the currently selected player unit. The unit should move between its origin and destination, acquire nearby enemy targets while patrolling, attack them with existing combat rules, and then continue its patrol route.

## Background

- Web Rustwar already supports Patrol as part of its broader RTS command set.
- Native iOS currently supports single selected player unit Move, Attack Move, Attack and Stop, plus production, rally, save/load and enemy AI.
- `RustwarCore` already owns unit orders, bounded attack-move acquisition, combat movement, damage, death cleanup and deterministic Swift tests.
- The iOS app should remain native SwiftUI/SpriteKit. Do not use `WKWebView` or Web code wrapping.

## Functional requirements

1. Extend `UnitOrder` with a Codable/Equatable/Sendable patrol order that stores both route endpoints and the active leg direction, for example `origin`, `destination` and `returning`.
2. Add `GameEngine.issuePatrol(to:) -> UnitCommandResult`:
   - requires an active selection;
   - requires the selected entity to be a player unit;
   - clamps the destination to map bounds;
   - stores the selected unit's current position as the origin;
   - starts by moving toward the destination;
   - writes the patrol order without changing selection.
3. Add patrol simulation in `GameEngine.updateUnitOrders`:
   - each update, find the nearest living enemy unit or building within the patrolling unit definition's `vision` range;
   - if a target is in acquisition range, reuse existing attack-order behavior for range closing, cooldown, damage and destroyed target cleanup;
   - if no target is in acquisition range, move toward the active patrol endpoint;
   - when the unit reaches the active endpoint, flip the patrol leg and keep the patrol order instead of clearing it.
4. Avoid using the existing move helper in a way that clears the patrol order on arrival. Add a movement helper that reports arrival or implement patrol movement explicitly.
5. Keep full-map AI target acquisition behavior unchanged. Patrol acquisition must be bounded to the patrolling unit's vision and must not make player units chase distant enemies across the whole map.
6. Keep `issueStop()` clearing patrol naturally through `order = nil`.
7. Add Swift tests proving:
   - patrol rejects missing selection and enemy/building selections using existing result semantics;
   - patrol moves toward its destination and then flips back toward the origin;
   - patrol acquires an enemy in vision and causes damage while preserving the route;
   - Stop clears an active patrol order;
   - JSON round-trip preserves an active patrol order.
8. Add iOS controller state for a pending patrol target:
   - Move, Attack Move, Attack, Patrol and Rally target modes must be mutually exclusive;
   - battlefield tap in patrol mode calls `issuePatrol(to:)`;
   - map switch, restart, load and Stop clear the pending patrol mode;
   - status text should distinguish Patrol from Move, Attack Move and Attack.
9. Add a native HUD button for Patrol near Move, Attack Move and Attack:
   - use a text-labeled SwiftUI `Button` with a system image;
   - maintain 44 pt minimum tap target;
   - keep existing Save/Load, Pause, Speed, Rally, Stop, production and cancel controls working.
10. Render patrol orders in SpriteKit with a distinct route line and marker, for example a cyan route between origin and destination plus a `P` marker at the active destination.
11. Preserve existing Move, Attack Move, Attack, Stop, Rally, production, production cancel, enemy AI, map switch/restart, pause/speed, tactical minimap, camera and Save/Load behavior.

## Non-goals

- No Web behavior change.
- No multi-unit patrol.
- No queued or Shift patrol.
- No patrol from tactical minimap.
- No guard, reclaim or transport command migration.
- No pathfinding, formation movement, collision avoidance or target priority matrix.
- No fog/radar integration.
- No save migration beyond preserving Codable behavior for newly saved v1.13 states.
- No third-party dependency or new build system.

## SwiftUI guidance

- Keep command state and command actions in `GameController`; do not put game command logic in `GameHUDView.body`.
- Prefer text-labeled buttons such as `Button("Patrol", systemImage: "...", action: controller.togglePatrolCommand)` for VoiceOver.
- Keep command controls compact and consistent with existing Move, Attack Move, Attack, Stop and Rally controls.
- Do not introduce UIKit or third-party libraries.
