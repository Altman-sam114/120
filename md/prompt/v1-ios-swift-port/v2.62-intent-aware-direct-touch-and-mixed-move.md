## 轮次目标

1. 选中至少一个己方 combat unit 时，主战场 44pt 触控容错区内的可见敌方单位/建筑必须优先于更近的友方实体被解析为攻击目标，避免点敌人变成 Select/Guard。
2. 主战场直接 tap、主战场 touch preview 和长按 context 使用同一敌方优先意图；保留 exact enemy 命中、当前视野/fog 过滤、其它 pending target 优先级和现有命令反馈。
3. Builder 与 combat unit 混合选择后点空地时，若所有所选 Builder 当前空闲，快速命令应先复用既有 `issueMove(to:)` 让 Builder 移动，再复用既有 `issueAttackMove(to:)` 让 combat unit 自动索敌前进；纯 combat、Builder-only、存在忙碌 Builder 和显式 Attack-Move pending 模式保持既有语义。
4. 更新 battlefield interaction hint/status，使玩家能知道混合快速命令会分别移动 idle Builder 与 attack-move combat unit。

## 实现边界

### 1. 敌方优先目标解析

- 在 `GameController` 内增加 presentation/controller-only 的只读 helper，复用 `selectionTargetVisibleToPlayer(at:includeEnemies:minimumHitRadius:targetTeam:)`。
- 只有存在 selected combat unit 时才提升敌方优先；优先尝试 exact enemy，再使用当前 `battlefieldTouchTargetWorldRadius`（或 context/map 传入的已有 radius）寻找可见敌方目标。
- `handleBattlefieldTap`、`battlefieldTouchPreview`、`contextTarget`/主战场 context 必须共享该优先路径；不能绕过 `GameEngine.issueAttack`、不能直接写 `UnitOrder`。
- 不改变无 combat selection 时已有的普通 selection/candidate 行为，不放宽 fog/visibility，也不让 radar contact 变成可攻击目标。

### 2. 混合快速移动

- 只在无实体目标、无 pending target 的 direct-tap 快速命令路径处理。
- 识别“至少一个 combat unit + 至少一个 Builder，且所有所选 Builder `order == nil`”时，先调用既有 `engine.issueMove(to:)`，再调用既有 `engine.issueAttackMove(to:)`；不要复制 Core 的 selection 集合或 formation 算法。
- 对外发布一次以 Attack-Move 为主的成功 feedback/confirmation，并给出能区分 Builder/combat 数量的状态；Move 失败时保留真实失败反馈。
- Builder 有任意现存 order 时保留旧的 combat-only Attack-Move 快速路径，避免本轮改变忙碌 Builder 的任务中断语义。
- 预览可以继续使用已有 attack-move intent；若改动文案，必须与实际派发一致。

### 3. 不变量

- `TouchSequenceOwner`、Spatial/multitouch/pinch/long-press 手势、callback generation、44pt 阈值和 Tactical Map 物理手势不变。
- `RustwarCore` public API、`GameState`、`UnitOrder`、formation、自动索敌、姿态、战斗数值、AI、生产、存档/JSON、Web 版不变。
- 生产建筑入口、升级、队列和 VoiceOver 不在本轮改动；“生产按钮不可用态”留给下一轮。
