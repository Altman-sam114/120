## 公开参考结论

公开 App Store 截图、Google 图片结果和 YouTube 移动端评测共同呈现出 Rusted Warfare 的关键战场语言：

- 高辨识度俯视 2D 战场，而不是抽象圆点或字母棋子。
- 地形保持清晰、低噪声，单位和建筑靠深色轮廓、朝向、炮塔/履带/舱体分层快速识别。
- 队伍色是局部装甲和识别条，不应把所有对象涂成同一个无细节色块。
- 弹道、炮口焰和命中反馈短促、明亮、立即消失，不形成持续发光线网。
- HUD 紧凑贴边，但本轮只处理主战场 SpriteKit 视觉，不重做 HUD。

这些参考只用于提炼视觉原则。禁止下载、提交、临摹或重新分发原作截图、视频帧、sprite、音频、logo 或其它受版权保护素材；本轮全部使用 SpriteKit 程序化几何和系统颜色实现原创剪影。

## 本轮目标

在不改玩法状态和存档格式的前提下，把原生 iOS 主战场从“圆形/圆角矩形 + 字母”临时占位表现提升为第一轮可辨识的程序化战场美术，并补齐短生命周期火力反馈：

1. 7 类现有单位都有明显不同的俯视剪影、前后方向、底盘与武器/工具层次。
2. 5 类现有建筑都有明显不同的工业/军事结构，完成度和升级等级能从外观读出。
3. 玩家与敌军同时具备高对比队伍色和非纯颜色的阵营识别细节。
4. 单位方向随移动、订单或可见目标改变；不向 `RustwarCore` 增加仅为渲染服务的持久化 heading。
5. 真实开火/受击状态变化触发短促的炮口焰、曳光或弹丸、命中闪光；不能继续把整个 reload 周期画成常亮火力线。
6. 选择环、HP 条、建造/升级进度、命令线、战争迷雾、雷达 signal 和覆盖圈保持清晰且行为不变。
7. 尊重 Reduce Motion，并保证临时特效和场景历史不会无限增长或跨 Restart / Load / Map 切换残留。

## 架构和状态边界

### 事实来源

- `GameState`、`UnitSnapshot`、`BuildingSnapshot` 和现有 definition 仍是玩法事实来源。
- 程序化外形只能读取 `type`、`team`、`position`、`order`、`weaponCooldown`、HP、`buildProgress`、`upgradeLevel`、`upgradeProgress` 和现有 definition。
- 朝向、上一帧 cooldown、上一帧 HP 和正在播放的 visual effect 都是 `BattlefieldScene` 的瞬态渲染状态，禁止编码进存档或回写 Core。
- `renderNow()` 和绘制 helper 只能显示状态，不得推进伤害、资源、AI、订单或其它模拟。

### 可见性

- 玩家实体继续始终绘制；敌方实体仍只能在 `playerVisibility` 当前可见时绘制。
- 任何 tracer、炮口焰、目标方向或命中效果都不得暴露当前不可见敌方的精确位置、类型或攻击关系。
- 只有在效果生成当下，射手与精确目标都满足现有玩家可见性规则时，才可绘制二者之间的 tracer/弹丸。
- 玩家实体受到不可见来源伤害时，可以在玩家实体自身位置显示受击闪光，但不得由此绘制到隐藏攻击者的连线、方向或外形。
- 战斗效果层必须位于实体层之上、雾层之下；已探索浅雾和未探索深雾仍能遮住效果。雷达 signal 层级和语义保持不变。
- 雷达 contact 仍只是青色信号点，不能被程序化实体剪影或战斗效果升级成真实敌方外形。

### 重置和生命周期

- Map 切换、Restart 和 Load 会推进既有 `mapRenderRevision`；当 map id 或 revision 改变时，必须清空朝向/cooldown/HP 历史、活动效果和其它 scene-only 缓存，并以当前快照重新播种，避免载入瞬间误报一轮开火/受击。
- 每帧要移除已经不存在实体的历史项，禁止字典随死亡和重开无限增长。
- 所有效果必须通过短 `SKAction` 序列自行 `removeFromParent()`，并设置小而明确的最大活动节点数或等价的有界策略。
- `renderNow()` 在同一 Core 快照上被重复调用时不得重复生成同一发炮火或同一次受击效果。

## 程序化视觉规格

### 通用规则

- 单位和建筑必须由少量 `SKShapeNode` / `CGPath` 组成的复合 `SKNode` 绘制，保留干净俯视 2D 风格；不使用 emoji、SF Symbols、字母标签或运行时生成位图冒充模型。
- `drawUnit` 和 `drawBuilding` 不再把 `definition.icon` 添加为实体中心文字。现有命令落点中的 A/P/G/R 等战术标记可保留，因为它们不是实体模型。
- 统一使用深色阴影/底边、主体中性色装甲、局部队伍色装甲板、窄高光和清晰外轮廓。不要把整个模型继续填成纯绿或纯红。
- 视觉 bounds 应大致围绕现有 unit `radius` / building `size`，不得让模型尺寸与 Core 命中范围严重脱节。
- 不依靠颜色作为唯一阵营区别：例如玩家使用单条中轴识别条/实心徽记，敌方使用双条或 V 形识别片；在灰阶下仍能区分。
- 选择反馈单独画在模型外侧，建议使用黄色分段环或角标，不得用选择描边覆盖模型自身轮廓。
- HP、建造和升级进度条继续使用现有事实值；位置要随新剪影调整，不能遮挡炮塔、天线或单位主体。
- 模型放大/缩小时不得出现文本溢出，也不得在正常相机 zoom 下小到只剩无差别色点。

### 7 类单位剪影

必须对 `UnitType.allCases` 的每个现有 case 显式处理，不允许 `default` 全部回退为同一个圆：

- `builder`：紧凑六边形或箱式工程底盘、前向双工具臂/叉、后部工具舱；轮廓偏短宽，不能像坦克。
- `scout`：轻型箭头/楔形车体、窄尾部、短前向武器或传感器；体型最轻、方向最醒目。
- `tank`：左右履带、中央装甲车体、独立炮塔和单长炮管；炮塔/炮管层必须高于底盘。
- `hover`：菱形或圆角楔形舱体、左右悬浮荚/能量带，不绘制履带；与 tank 一眼可分。
- `aaTank`：履带底盘、中央炮塔和对称双炮管/双防空臂；不能只靠 AA 字母区别。
- `artillery`：宽履带或支撑底盘、明显更长的炮管、后部炮架/驻锄；轮廓重量和射程感应强于 light tank。
- `gunboat`：长船体、尖船首、短船尾、中央炮座和两侧水线/舷缘；不画成陆地圆车。

单位容器的局部正方向统一，例如全部朝局部 `+x`，再由单一 heading helper 设置 `zRotation`，避免每个类型使用不同坐标约定。

### 单位朝向

按以下优先级推导 scene-only heading：

1. 若本帧相对上一帧位置有超过微小阈值的位移，朝向实际位移。
2. 否则显式 `.attack` 且目标当前可见时，朝向目标。
3. 否则对 `.move`、`.attackMove`、`.patrol` 当前端点、`.guardTarget`、`.build`、`.repair`、`.reclaim` 使用可合法取得的订单目标方向。
4. 都不可用时保留该 id 的上次有效 heading；首次出现则用按 team 确定的稳定默认方向。

计算必须使用 world-to-sprite 的 y 轴翻转，避免单位实际向下移动时模型朝上。接近零长度向量不得产生 NaN。朝向缓存仅存在 Scene 内，并在重置时清空。

### 5 类建筑剪影

必须对 `BuildingType.allCases` 的每个现有 case 显式处理：

- `command`：大型八边形/堡垒底座、中央指挥核心、四角装甲或天线节点；保持最强基地视觉重量。
- `extractor`：资源井底座、同心采集环、中心泵/涡轮和辐条；T2/T3 分别增加可见环带、能量段或顶部层级，不能只靠 HUD 文本表现升级。
- `landFactory`：宽矩形工业底座、中央生产/出入口、左右模块和方向性跑道/门；与 Command Center 尺度和轮廓清楚区分。
- `turret`：固定基座环、旋转炮塔头和炮管。发生可见射击时炮管朝向目标；没有目标时保留 scene-only 最近朝向或稳定默认方向。
- `radar`：基座、立柱和明显雷达碟/阵列；T2 增加第二道阵列、外环或更强高光层级。

未完成建筑不能只是整体降低 alpha：还要通过虚线/分段框架、脚手架角标、未闭合外壳或等价几何显示“施工中”，同时保留现有 `buildProgress` 条。完成建筑不显示施工框架。

### 阵营、选择和层次

- 建议把 team color 收敛为局部高饱和识别色，把主体装甲使用不同亮度的钢灰/深灰；玩家绿和敌方红必须在草地、沙地、岩地、水面与熔岩上都有足够对比。
- 每个实体至少有底部软阴影或深色 footprint，主体外轮廓，主体装甲层，队伍识别层和类型特征层。
- 阴影必须轻量，禁止给每个实体添加昂贵 blur/filter。
- 多选集合仍应全部显示选择反馈；模型选择外环不能改变 Core 的选择集合或 hit testing。

## 战斗火力反馈规格

### 事件判定

不新增 Core event model。本轮在 Scene 内观察现有快照变化：

- 保存每个存活单位/武装建筑上一帧 `weaponCooldown`。
- 只有当 cooldown 从较低值明显上跳到接近 definition `reloadTime` 时，才视为一次新开火；仅仅 `weaponCooldown > 0` 不能每帧重复生成效果。
- 保存每个实体上一帧 HP；只有 `currentHP < previousHP` 时，在当前可见实体位置生成一次受击效果。
- 初次出现、Map/Restart/Load 后重新播种的快照不产生假开火或假受击。
- 同一快照上的重复 `renderNow()` 不重复触发。

### 效果表现

- 新开火至少生成一个 0.08-0.18 秒的高亮炮口焰；有合法可见精确目标时，再生成短曳光或弹丸。
- 曳光/弹丸持续时间应短，并按距离 clamp 在约 0.08-0.28 秒范围；不能使用贯穿整个 reload 周期的常亮红线。
- 命中效果使用小型亮核 + 外环/碎片或等价程序化几何，正常模式总时长建议不超过 0.35 秒。
- tank / turret 使用单发炮口和中等命中；aaTank 使用双短曳光；artillery 使用更大的炮口焰、较醒目的短弹丸和更大但仍克制的命中环；scout / builder 保持较小反馈；gunboat / hover 有不同色温或宽度，但不得造成一屏高亮噪声。
- 可以保留 `drawAttackOrder` 的命令关系线和目标圈，但它们是命令 UI，不得被当作开火特效；既有 `drawTurretFire` 应改为事件驱动短效果或移除其持续 reload 线语义。
- 自动 Attack-Move / Patrol / Guard 若没有 Core 暴露的精确目标，不得猜测并绘制到隐藏目标的连线。此时可只画射手处炮口焰，并由受伤实体自己的 HP delta 显示命中。

### Reduce Motion

- `BattlefieldView` 读取 SwiftUI `@Environment(\.accessibilityReduceMotion)`，在 `.task` 和值变化时同步给 `BattlefieldScene`。
- Reduce Motion 开启时，不让弹丸跨屏移动、不做明显 scale/rotation 动画；改为短暂 opacity-only 炮口/命中闪光，仍保留必要战斗信息。
- 该桥接只控制视觉表现，不修改暂停、速度或 Core 模拟。

## 性能和代码质量

- `BattlefieldScene` 已是 `@MainActor`，保持所有可变视觉历史在主 actor；不要引入 GCD、timer 或后台共享状态。
- 每个实体使用有限、可读的节点数量；优先复用小 helper 和复合 `CGPath`，不要为装饰创建几十个节点。
- 不要在每次 render 为不变轮廓做昂贵路径计算；可按 type/radius/size 复用稳定 path 或集中 factory，但不要为此引入大范围架构重写。
- 临时效果只在状态跃迁时创建，不在每帧为 `weaponCooldown > 0` 创建。
- 不使用 `SKEmitterNode` 无上限喷发、Core Image filter、动态模糊或每实体光照系统。
- helper 命名应表达 unit body、building body、selection、heading、fire transition 和 effect lifecycle 的职责；只给不直观的 cooldown/HP 跃迁判定添加简短注释。
- 保持 strict concurrency 可编译，不使用 force unwrap，不吞掉错误，不新增 UIKit 依赖。
- `BattlefieldView` 的 SwiftUI body 不加入排序、过滤、状态推导等玩法逻辑；仅做 Reduce Motion 环境值桥接。

1. `drawUnit` / `drawBuilding` 不再用 `definition.icon` 字母作为实体主体。
2. `builder/scout/tank/hover/aaTank/artillery/gunboat` 七种单位仅看剪影即可互相区分，并有统一正确的朝向坐标。

5. 选择外环、HP、建造/升级进度均未被模型遮挡，多选全部有反馈。
6. 移动单位的车头/船首朝实际位移方向；静止攻击单位朝可见目标；零向量不产生异常旋转。

8. 开火效果短促并自行移除，效果历史有界，Restart / Load / Map 切换不残留旧特效或朝向。

10. Reduce Motion 开启时没有跨屏弹丸移动或明显缩放动画，只用短 opacity 反馈。
11. Core、存档形状、玩法数值、目标选择、伤害时机和 Web 行为无改动。
