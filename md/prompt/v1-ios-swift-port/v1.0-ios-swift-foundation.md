# v1.0 / iOS Swift migration foundation

## 1. Version

- Version: `v1.0`
- Stage: iOS / Swift migration foundation.
- Reason: the current project is a mature pure web Canvas RTS prototype. Moving toward a native iOS game is a platform-level milestone, so this starts a new major version instead of continuing the v0.x workflow/documentation series.

## 2. Current Progress Summary

Rustwar is currently a browser-only RTS prototype:

- `index.html` provides the DOM shell, two canvases, HUD, command panel, sandbox panel, stats panel and buttons.
- `styles.css` provides the web layout and responsive panel styling.
- `app.js` is the single runtime source of truth. It contains config tables, map generation, centralized `state`, `camera`, `input`, `selectedIds`, `controlGroups`, command dispatch, simulation update, AI, rendering, save/load and sandbox import/export.
- The game already includes maps, economy, factories, units, buildings, combat, fog of war, radar, minimap, AI difficulty, campaign/survival/challenge/sandbox modes, stats, save/load and sandbox JSON.
- Collaboration is now `main` direct push plus GitHub Actions result package. Agent B implements and pushes to `origin/main`; Agent C downloads and verifies the matching artifact.

The existing web game must remain runnable by directly opening `index.html`. The iOS work starts as a native Swift port path, not a replacement commit that deletes the web prototype.

## 5. Non-goals

Do not attempt full game parity in this version.

Out of scope for v1.0:

- Full migration of all web `app.js` gameplay systems.
- Complete AI behavior.
- Full combat/projectile simulation.
- All unit/building production queues and upgrades.
- Save/load parity and sandbox import/export parity.
- Web-to-Swift automatic transpilation.
- WebView packaging of the current webpage.
- Third-party engines, package managers, code generators, backend services or network dependencies.
- Deleting or replacing the web prototype.
- PR flow or non-`main` branch workflow.

## 6. Architecture Basis

Current web truth:

- External input enters through DOM, Canvas, URL parameters, localStorage and sandbox JSON.
- `app.js` stores match facts in `state`, camera in `camera`, input mode in `input`, selection in `selectedIds`, groups in `controlGroups`.
- `loop(now)` calls `update()`, conditional `refreshUI()` and `render()`.
- `render()` must display only; simulation belongs in `update()`.

Native iOS target for this version:

- Swift game state should become the iOS source of truth for the native app.
- Keep model/data logic outside SwiftUI view bodies.
- Use an `@MainActor` shared game controller/engine if using SwiftUI observation.
- Views should be split by type/file; do not put many structs/classes/enums into one Swift file.
- Prefer `@Observable` + `@State` ownership for SwiftUI state where available. Avoid legacy `ObservableObject`/`@Published` unless there is a clear compatibility reason.
- Keep rendering and simulation separated:
  - `RustwarCore` owns data models and deterministic small-step logic.
  - iOS scene/view reads a snapshot and draws.
  - Touch gestures dispatch camera/selection commands into the engine.
- Use flexible layouts, not `UIScreen.main.bounds`.
- Maintain at least 44x44 touch targets for HUD controls.

## 8. Implementation Steps

1. Start from a clean synchronized `main`.
   - Run `git fetch origin`.
   - Run `git switch main`.
   - Run `git pull --ff-only origin main`.
   - Run `git status --short --branch`.
   - If `origin` is missing, auth fails, or remote access fails, stop push/cloud steps and report the blocker.

2. Audit the existing web runtime enough to map the first Swift data model.
   - Read `README.md`, `AGENTS.md`, `update_log.md`, `md/flow/flow.md`, `md/flow/flowchart.md`, `md/test/test.md`.
   - Inspect `app.js` config/state sections, especially maps, teams, terrain, initial entities and income.

3. Build `RustwarCore`.
   - Port only the minimal data needed for the first iOS screen and state tick.
   - Prefer value types for immutable definitions and entity snapshots.
   - Use `Double` for world coordinates and economy values.
   - Avoid force unwraps and silent error swallowing.
   - Add tests that can run with Command Line Tools using `swift test --package-path swift/RustwarCore`.

4. Build the iOS app shell.
   - Create an iOS app target that imports `RustwarCore`.
   - Use SwiftUI for root/HUD and a first-party renderer for the battlefield.
   - Render terrain, resources and initial units/buildings from Swift state.
   - Implement pan/zoom and simple selection feedback.
   - Keep UI compact and game-first; do not make a marketing landing page.

5. Update documentation.
   - Be explicit that v1.0 is a native iOS foundation, not full gameplay parity.
   - Document how to open/build the iOS app.
   - Document local validation limits if Xcode is unavailable on the local machine.

6. Update CI if feasible.
   - Preserve existing artifact contract for Agent C.
   - Include Swift package and iOS build outcomes when actually run.
   - If workflow changes, run YAML parsing locally.

7. Commit and push only related files.
   - Confirm current branch is `main`.
   - Confirm target remote is `origin/main`.
   - Stage only v1.0 files.
   - Commit message should start with `v1.0:` and match `update_log.md`.
   - Push directly with `git push origin main`.

## 9. Local Test Requirements

Always run:

```sh
git diff --check
```

Run for Swift core:

```sh
swift test --package-path swift/RustwarCore
```

Run if Xcode is available:

```sh
xcodebuild -list -project ios/RustwarIOS/RustwarIOS.xcodeproj
xcodebuild -project ios/RustwarIOS/RustwarIOS.xcodeproj -scheme RustwarIOS -destination 'generic/platform=iOS Simulator' CODE_SIGNING_ALLOWED=NO build
```

Run if `app.js` changes:

```sh
node --check app.js
```

Run if `.github/workflows/ci-results.yml` changes:

```sh
ruby -e 'require "yaml"; YAML.load_file(".github/workflows/ci-results.yml"); puts "yaml ok"'
```

If local `xcodebuild` is unavailable because only Command Line Tools are selected, report that exact limitation. Do not describe the iOS app as locally built unless `xcodebuild` really succeeded.

## 11. Acceptance Criteria

v1.0 is acceptable only if:

- The existing web game remains present and directly runnable.
- A native Swift/iOS project path exists under `ios/` and is documented.
- A Swift core package exists under `swift/RustwarCore/`.
- The Swift core has tests for initialization and basic logic.
- The iOS app code is native Swift/SwiftUI plus first-party rendering, not a web wrapper.
- The native app has a battlefield screen sourced from Swift state, with basic HUD and touch interaction.
- Docs reflect the new dual-platform project shape.
- Local validation results are reported with exact commands.
- Cloud validation is triggered or a concrete blocker is reported.
- Agent C can later verify the exact `origin/main` commit and artifact.

## 12. Risks

- Full RTS parity is too large for one version. Keep this version as foundation plus visible native battlefield.
- Xcode may be unavailable locally. Swift package tests can still validate core logic, but iOS target build may need cloud macOS runner or a machine with full Xcode.
- Manual Xcode project files are easy to break. Keep the project minimal and validate with `xcodebuild` when possible.
- Updating CI from Ubuntu to macOS may change runtime and cost. If done, preserve the artifact shape and keep logs explicit.
- Duplicating logic between JavaScript and Swift can drift. Start with a small Swift core and document which parts are authoritative for iOS v1.0.
