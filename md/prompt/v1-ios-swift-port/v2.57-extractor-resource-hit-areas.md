# v2.57 Extractor Resource Hit Areas

## 版本与轮次

- 版本：`v2.57`
- 主题：pending Extractor 资源点触控容错与预览一致性
- 目标分支：`main`
- 实现提交信息：`v2.57: expand extractor resource hit areas`
- 前置：v2.56 实现与验收记录已在 `origin/main` 完成并通过最新 Actions artifact。

## 本轮目标

1. pending Build Extractor 时，battlefield preview、battlefield commit 和 Tactical Map commit 共用同一资源点最小命中半径。
2. Battlefield 继续沿已有 44pt touch target 计算 world radius；Tactical Map 继续沿已有约 16pt screen diameter 换算 world radius，让小型资源 marker 更接近 Rusted Warfare 式易点按目标。
3. 命中资源点后仍只调用既有 `resourceTarget` / `issueBuildExtractor`，占用资源点、已 claimed、已有 Extractor、invalid retry 和 pending 状态保持。

## 非目标与架构边界

- 不修改 `RustwarCore` 的默认 `resourceTarget` 半径、资源数据、建造规则、存档/JSON、命令结果、AI、战斗或 Web 版。
- 不扩大普通 context tap、普通 map camera tap、Reclaim、Attack、其它 pending building target 或 selection target 的命中范围。
- 不改变 `TouchSequenceOwner`、拖动/长按/pinch、fog/visibility、最近目标排序或 command confirmation。

## 实现契约

- `GameController` 的 pending Extractor 入口必须把 battlefield `battlefieldTouchTargetWorldRadius` 或 Tactical Map 传入的 `minimumHitRadius` 转成 Core `resourceTarget(at:maxDistance:)` 的最小距离；非 pending Extractor 仍使用既有默认值。
- `battlefieldTouchPreview` 与最终提交必须调用相同半径语义，不能出现预览 invalid 但提交成功或反向不一致。
- Tactical Map 只在 `isAwaitingBuildExtractorTarget` 时复用既有 pending target screen diameter；普通 map tap 仍居中相机或沿原命令路径执行。

## 云端唯一验证

- 本地禁止 SwiftPM test、Swift typecheck、Xcode build/list、Simulator、Preview、浏览器、截图和 `git diff --check`；只做只读源码/状态范围审查。
- Agent C 只验收最新 `origin/main` SHA 的未加密 artifact 到 `/private/tmp/rustwar-c-review-<run_id>/`，核对 manifest、JUnit、日志、失败摘要、双架构 build、production/combat 双启动、横屏归一化和双 PNG。
- 代码复核确认 pending Extractor 的 battlefield preview/commit/map commit 三路共用半径，Core 默认选择和其它 target command 不变；静态 PNG 不能证明真实资源 marker 点按手感。

## 已知风险

- CI 没有真实触摸注入、XCUITest、VoiceOver、Dynamic Type、Reduce Motion 或多设备矩阵；artifact 只能证明编译、启动和静态构图，不能证明手指落点命中率。
