# v1.14 / iOS native guard command foundation

## Agent A brief

Version: `v1.14`

Goal: add a native iOS single-unit Guard command so the SwiftUI/SpriteKit app can order the currently selected player unit to escort a friendly unit or building. The guard unit should keep a stable offset near the friendly target, acquire nearby enemy targets while guarding, attack them with existing combat rules, and then continue guarding.

## Background

- Web Rustwar already supports Guard/Escort as part of its broader RTS command set.
- Native iOS currently supports single selected player unit Move, Attack Move, Patrol, Attack and Stop, plus production, rally, save/load and enemy AI.
- `RustwarCore` already owns unit orders, bounded acquisition for Attack Move and Patrol, combat movement, damage, death cleanup and deterministic Swift tests.
- The iOS app should remain native SwiftUI/SpriteKit. Do not use `WKWebView` or Web code wrapping.

## Functional requirements

1. Extend `UnitOrder` with a Codable/Equatable/Sendable guard order. Avoid using the Swift keyword `guard` as the case name; use a name such as `guardTarget(targetID:offset:)`.
2. Store:
   - the friendly guarded entity ID;
   - a stable offset from the guarded entity, so the guard unit can resume a position near that target after moving or fighting.
3. Add `UnitCommandResult.invalidGuardTarget` or equivalent explicit result semantics for invalid guard targets.
4. Add `GameEngine.issueGuard(targetID:) -> UnitCommandResult`:
   - requires an active selection;
   - requires the selected entity to be a player unit;
   - requires the target to be a living friendly unit or building;
   - rejects guarding self;
   - computes a small stable offset near the target;
   - writes the guard order without changing selection.
5. Add guard simulation in `GameEngine.updateUnitOrders`:
   - if the guarded entity no longer exists, is destroyed, or is no longer friendly, clear the guard order;
   - each update, find the nearest living enemy unit or building within either the guard unit definition's `vision` range or a bounded area around the guarded entity;
   - if a target is in acquisition range, reuse existing attack behavior for range closing, cooldown, damage and destroyed target cleanup without replacing the guard order with a persistent attack order;
   - if no enemy target is in acquisition range, move toward the guarded entity position plus the stored offset;
   - when the guard unit is close to its guard position, keep the guard order active instead of clearing it.
6. Preserve existing Move, Attack Move, Patrol, Attack, Stop, Rally, production, production cancel, enemy AI, map switch/restart, pause/speed, tactical minimap, camera and Save/Load behavior.
7. Add Swift tests proving:
   - guard rejects missing selection, enemy/building selections, enemy targets and self-targets;
   - guard accepts a friendly unit or building target and preserves player selection;
   - guard moves the unit toward the guarded target offset without clearing the order;
   - guard acquires an enemy near the guard unit or guarded entity and damages it while preserving the guard target;
   - guard clears if the friendly target is destroyed;
   - Stop clears an active guard order;
   - JSON round-trip preserves an active guard order.
8. Add iOS controller state for a pending guard target:
   - Move, Attack Move, Patrol, Attack, Guard and Rally target modes must be mutually exclusive;
   - battlefield tap in guard mode calls `issueGuard(targetID:)` for the tapped entity;
   - tapping an enemy, empty ground or the selected unit in Guard mode should report a friendly target requirement;
   - map switch, restart, load and Stop clear the pending guard mode;
   - status text should distinguish Guard from Move, Attack Move, Patrol and Attack.
9. Add a native HUD button for Guard near other unit commands:
   - use a text-labeled SwiftUI `Button` with a system image;
   - maintain 44 pt minimum tap target;
   - keep existing Save/Load, Pause, Speed, Rally, Stop, production and cancel controls working.
10. Render guard orders in SpriteKit with a distinct line and marker, for example a green line from guard unit to guarded entity plus a `G` marker.

## Non-goals

- No Web behavior change.
- No multi-unit guard.
- No queued or Shift guard.
- No guard from tactical minimap.
- No builder repair-on-guard behavior in this round.
- No transport, reclaim or repair command migration.
- No pathfinding, formation movement, collision avoidance or target priority matrix.
- No fog/radar integration.
- No save migration beyond preserving Codable behavior for newly saved v1.14 states.
- No third-party dependency or new build system.

## SwiftUI guidance

- Keep command state and command actions in `GameController`; do not put game command logic in `GameHUDView.body`.
- Prefer text-labeled buttons such as `Button("Guard", systemImage: "...", action: controller.toggleGuardCommand)` for VoiceOver.
- Keep command controls compact and consistent with existing Move, Attack Move, Patrol, Attack, Stop and Rally controls.
- Do not introduce UIKit or third-party libraries.
