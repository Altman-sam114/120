# v1.15 iOS native repair command foundation

## Agent A prompt for Agent B

### Goal

Add a native Swift/iOS single-builder Repair command foundation, moving the iOS migration one step closer to the Web RTS command set without changing the playable Web Canvas prototype.

The v1.15 slice should let one selected player Builder repair one damaged friendly unit or building from the native iOS HUD. The shared Swift core must own validation, order state, movement into range, hit point restoration, target cleanup, and tests. SwiftUI and SpriteKit should only route input and render the order.

### Current baseline

- Web repair reference:
  - `app.js` `issueRepair(units, target, append)` assigns `{ type: "repair", targetId }` only for engineering units and same-team targets.
  - Web repair update clears missing/dead/full targets, moves into 125 world units, then restores `repairPower * dt`.
  - Web Builder `repairPower` is 18.
  - Web Stop cancels repair by clearing the unit order.
- Native v1.14 already has:
  - `UnitOrder.move`, `.attack`, `.attackMove`, `.patrol`, `.guardTarget`.
  - `GameEngine.issueGuard(targetID:)`, `issueStop()`, core order updates, target cleanup, Swift tests.
  - iOS pending target modes for Move / Attack Move / Patrol / Guard / Attack / Rally.
  - SpriteKit order lines for Move / Attack Move / Patrol / Guard / Attack / Rally.

### Scope

Implement only this native foundation:

1. `UnitOrder.repair(targetID:)`.
2. `UnitCommandResult.selectedEntityCannotRepair` and `invalidRepairTarget`.
3. `GameEngine.issueRepair(targetID:)`.
4. Repair simulation for one selected player Builder:
   - selected entity must be a player unit of type `.builder`;
   - target must be a living friendly unit or building;
   - target must not be the selected builder itself;
   - target must be damaged (`hitPoints < maxHitPoints`);
   - move toward target while outside repair range;
   - repair at 18 HP/second;
   - clamp HP to `maxHitPoints`;
   - clear the repair order when target is missing, dead, hostile, self, or full HP.
5. iOS HUD/controller:
   - show Repair only when a player Builder is selected or Repair targeting is pending;
   - tap Repair to enter target mode, tap again or Stop to cancel;
   - next battlefield tap must hit-test a friendly damaged target and call `issueRepair(targetID:)`;
   - Load, Restart, map switch, and Stop must clear pending Repair mode through the existing central helper.
6. SpriteKit:
   - render a distinct repair line/marker for `.repair(targetID:)`.
7. Swift tests:
   - JSON round-trip preserves repair order;
   - invalid selections and invalid targets are rejected;
   - damaged friendly unit and building targets are accepted;
   - out-of-range builder moves toward the target and keeps the order;
   - in-range target is repaired and capped at max HP;
   - order clears when the target becomes full or destroyed;
   - Stop clears a repair order.
8. Documentation:
   - update README native iOS capability and controls;
   - update `md/flow/flow.md`, `md/flow/flowchart.md`, `md/test/test.md`;
   - append v1.15 to `update_log.md`.

### Non-goals

- Do not change `index.html`, `styles.css`, or `app.js`.
- Do not use `WKWebView`.
- Do not implement Reclaim.
- Do not implement build placement/build-assist in native iOS.
- Do not implement repair tank aura, repair platform aura, self-repair, Guard auto-repair, or auto-acquire repair targets.
- Do not add metal cost/resource drain for repairs in this slice.
- Do not implement multi-unit Repair, Shift/queued orders, tactical minimap Repair targeting, fog/radar interaction, or formal particle effects.
- Do not refactor the core command architecture beyond what this repair order requires.

### Suggested implementation notes

- Keep repair constants private to `GameEngine`, e.g. 125 repair range and 18 HP/s repair rate, matching the Web Builder baseline.
- Prefer a separate private repair target helper instead of stretching `CombatTarget`; repair needs `hitPoints` and `maxHitPoints`.
- Use a private `applyRepair(_:to:)` helper that mutates either units or buildings and clamps to max HP.
- Keep UI status text specific: "Repair order issued", "Builder required", and "Damaged friendly target required" are enough.
- Use an SF Symbol such as `wrench.and.screwdriver` for the Repair button and a cyan/green `+` or `R` marker for the SpriteKit order line.
