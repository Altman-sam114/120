## Goal

1. Make normal battlefield tapping feel like a direct-touch RTS:
   - Tap a player unit or building to select it.
   - With one or more living player units already selected, tap a currently visible enemy unit/building to issue explicit Attack immediately.
   - With one or more living player units already selected, tap open battlefield ground to issue Attack Move immediately. Units move toward their formation destinations and automatically engage targets according to their existing stance.
2. Keep the current selection after a successful or rejected direct Attack / Attack Move attempt; issuing a direct command must not replace the selection with the enemy or clear it on open ground.
3. Keep friendly selection exact: Replace/Add behavior, primary selection, and double-tap nearby same-type selection remain available when tapping a player unit. Tapping a player building still selects it and immediately exposes the existing production/upgrade controls through the current dock derivation.
4. Preserve every pending command mode and the complete long-press context command path.
5. Reuse existing Core APIs, status text, command feedback, command confirmation, fog-filtered hit testing, formation assignment, stance rules, and render revision flow. Do not create a second gameplay state or duplicate feedback events.
6. Validate only with the exact pushed `origin/main` commit's GitHub Actions `Rustwar CI Results` v1.2 artifact. All local tests/builds/Simulator/Preview/browser checks remain forbidden.

## Exact Tap Decision Table

Apply this ordering in `handleBattlefieldTap(screenPoint:viewportSize:)`:

| Priority | Condition | Required result |
| --- | --- | --- |
| 1 | `isAwaitingAreaSelection` | Keep the existing warning and return. Do not issue a direct command. |
| 2 | Any existing pending point command | Keep `handlePointCommand(at:)` behavior and return. |
| 3 | Any existing pending entity target command | Keep `handleSelectionTargetCommand(at:)` behavior and return. |
| 4 | Any existing pending Builder target command | Keep `handleBuilderTargetCommand(at:)` behavior and return. |
| 5 | No pending command, tap hits a living player unit/building | Keep the existing normal selection path. Preserve Replace/Add semantics and player-unit double-tap same-type detection. Never turn this tap into Guard or Repair. |
| 6 | No pending command, at least one living player unit is already selected, tap hits a currently visible enemy unit/building | Call existing `GameEngine.issueAttack(targetID:)`; preserve selection; use existing Attack status, success/warning feedback, and `.attack` confirmation at the target position exactly once. |
| 7 | No pending command, at least one living player unit is already selected, no selectable unit/building is hit | Call existing `GameEngine.issueAttackMove(to:)`; preserve selection; use existing Attack Move status, success/warning feedback, and `.attackMove` confirmation at the tapped world point exactly once. A wreck/resource under the finger must not silently become Reclaim/Build; those remain explicit pending or long-press context actions. |
| 8 | No pending command and no living player unit selected | Keep normal selection behavior. Tapping a player entity selects it; tapping a visible enemy follows the existing ordinary selection behavior; an empty tap uses existing selection mutation semantics (`Replace` clears, `Add` preserves). A building-only selection must never issue a unit command on empty ground. |

Additional invariants:

- Visibility remains authoritative. Use `selectionTargetVisibleToPlayer(at:includeEnemies:)`; radar-only or fog-hidden enemies cannot be directly attacked. If no visible entity target is returned while player units are selected, the tap is an Attack Move to that world point, not a precise fog attack.
- Mixed valid selection containing player buildings plus at least one living player unit may command only the units through the existing Core filtering; do not mutate the selection first.
- A friendly tap always wins over the direct empty-ground branch. Do not issue Attack Move and then select the friendly.
- A direct command consumes the tap. It must clear/update double-tap tracking appropriately so the command tap cannot combine with a later friendly double tap.
- Direct Attack is manual intent and remains valid for Hold Fire units. Direct Attack Move obeys Hold Fire and therefore moves without automatic acquisition; Aggressive/Defensive use their existing automatic engagement distances.
- The explicit Move button remains plain `.move`, with no automatic acquisition. The explicit Attack Move button and keyboard shortcut remain available and unchanged.

## Risk Controls

- **Friendly tap regression:** If direct routing runs before team discrimination, tapping a friendly can issue Attack Move instead of selecting. Resolve the target once and return false for `team == .player`.
- **Building-only accidental command:** Checking only nonempty selection lets a selected factory issue an invalid unit command and prevents empty-tap clearing. Require at least one living selected player unit.
- **Fog information leak:** Do not use unrestricted hit tests for enemies. Keep `selectionTargetVisibleToPlayer` as the only entity source.
- **Context semantic leak:** Do not reuse `issueContextCommand`; it contains Repair/Guard/Reclaim/Build/Rally/plain Move semantics that ordinary taps must not gain.
- **Feedback duplication:** Direct helper and caller must have one owner for status, haptic revision, confirmation, tap-history clearing, and render revision.
- **Hold Fire misunderstanding:** Attack Move still issues and moves, but automatic acquisition remains disabled. Manual direct Attack must still work.
- **Screenshot overclaim:** CI's default paused `No selection` screenshot cannot trigger any direct command. Build and code review are evidence for routing; screenshot only proves launch/nonblank/layout unless a future interaction harness is added.
- **Shared worktree:** Do not touch or stage the user's `project.pbxproj` or `.wp` changes.
