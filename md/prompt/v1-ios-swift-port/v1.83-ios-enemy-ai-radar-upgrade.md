# v1.83 iOS Enemy AI Radar Upgrade

## Agent A Prompt

Role: Agent B implements this prompt on `main`, then Agent C validates the latest `origin/main` GitHub Actions artifact.

## Goal

Extend the native Swift/iOS AI migration so red enemy AI can start the existing Radar Station T2 upgrade after its basic economy, factory, turret foothold, and completed Radar Station are in place.

## Non-goals

- Do not change Web Canvas behavior in `app.js`.
- Do not add a new iOS HUD command or expose enemy controls to the player.
- Do not add upgrade cancellation, a general AI upgrade tree, or new Radar T2 values.
- Do not use `WKWebView` or web wrapping.
- Do not make radar contacts reveal selectable or attackable fog targets.

## Required implementation

- Keep `GameEngine.queueBuildingUpgrade()` player-only and selection-gated.
- Extract the metal deduction and `upgradeProgress = 0` mutation into a private helper that can be reused by enemy AI without relaxing player command validation.
- Add enemy AI radar upgrade logic in `updateEnemyAI()` after `updateEnemyRadarConstruction()` and before reclaim/production.
- Enemy AI may queue a Radar Station T2 upgrade only when:
  - enemy AI is enabled,
  - red has at least one living Land Factory,
  - red has at least the existing extractor threshold used for additional factory/radar decisions,
  - red has the existing turret foothold limit,
  - a red Radar Station is living, completed, not already upgrading, and has a next upgrade,
  - red has enough metal for the upgrade.
- Deduct red metal immediately when the upgrade is queued.
- Let the existing `updateBuildingUpgrades(deltaTime:)` path complete the upgrade and let `GameDefinitions.building(for:)` continue to drive effective vision/radar values.
- Do not change `GameStateVisibility`, `BuildingSnapshot` Codable compatibility, or Radar T2 balance values.

## Required tests

Add Swift core tests for:

- Enemy AI queues Radar Station T2 when economy/factory/turret/radar prerequisites and enough metal exist.
- Queuing deducts 780 enemy metal, records `upgradeProgress == 0`, preserves player selection, and does not touch player Radar Stations.
- Enemy AI waits when metal is insufficient, radar is incomplete, radar is already upgrading, radar is fully upgraded, or enemy AI is disabled.
- The enemy upgrade progresses through the existing update path and completes with `upgradeLevel == 2`, `maxHitPoints == 520`, and enemy radar coverage range `1360`.
- Existing red Radar Station construction behavior remains capped at one station.

## Local checks

Agent B must run and report:

- `git diff --check`
- `node --check app.js` if `app.js` changed; running it even when unchanged is acceptable.
- `swift test --package-path swift/RustwarCore` if local SwiftPM works; if local toolchain blocks, report the exact error and run direct Swift parse/typecheck fallbacks.
- Because this is Core-only and does not edit `ios/RustwarIOS/`, iOS build can be left to cloud CI unless local workflow chooses to run it. If local Xcode is unavailable, report the exact limitation.

## Push and Agent C validation

Agent B must commit only related files on `main` and push directly to `origin/main`.

Agent C must validate only the latest `origin/main` commit and its matching GitHub Actions run. Download the unencrypted CI artifact to `/private/tmp/rustwar-c-review-<run_id>/`, then verify:

- manifest branch is `main`
- manifest commit SHA matches latest `origin/main`
- manifest run id and attempt match the downloaded run
- JUnit/test summary has no failures
- build log contains the expected Web, SwiftPM, and iOS checks
- artifact name is recorded in the final report

If validation fails, return to Agent B for an additional fix commit on `main`.
